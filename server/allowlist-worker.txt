# Binaries an EPHEMERAL WORKER container is permitted to run, via
# run_in_directory() -- checked in the coordinator's own process
# (bash_mcp_server.py) before that worker container is ever started,
# same as allowlist.txt's own check for run_command(), just against a
# separate, worker-scoped list. The worker itself has no allowlist
# logic of its own -- see worker/Dockerfile's own docstring for why.
#
# Split from the coordinator's own allowlist.txt 2026-08-09 (see that
# file's own header for the full reasoning): this list is allowed to
# be WIDER than the coordinator's, specifically because the worker's
# own privilege ceiling is much lower -- no docker CLI at all (see
# worker/Dockerfile), ephemeral, discarded after one call. A
# capability added here does not carry over to run_command()/the
# coordinator automatically -- that's the entire point of the split.
#
# One name per line; blank lines and '#' comments are ignored. Lives
# under /app in the COORDINATOR's own image (COPY'd there, not the
# worker's -- this file governs what the coordinator is willing to
# LAUNCH a worker with, it isn't read by the worker itself). Changing
# it needs an image rebuild (make build/make start).
#
# Deliberately does NOT include `docker` -- unlike allowlist.txt's own
# entry, this isn't "harmless because the worker image happens to lack
# the CLI today," it's an explicit statement of intent now that the
# two lists are genuinely separate: a worker-side capability should
# never include docker/root-equivalent host access, regardless of
# what today's worker image does or doesn't have installed.
