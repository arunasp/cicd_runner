# Binaries the COORDINATOR itself is permitted to run directly, via
# run_command() -- this container has real docker-socket access (see
# server/Dockerfile's own docstring), so this list is deliberately
# kept as narrow as possible, separate from what an ephemeral worker
# is allowed to do via run_in_directory() (see allowlist-worker.txt).
#
# Split into two files 2026-08-09, per Arunas's own explicit
# direction: previously this single file gated BOTH run_command() and
# run_in_directory(), which meant anything added for a worker-side
# need (e.g. bash, for Autotools regeneration) was also automatically
# granted to the coordinator -- the one container holding docker-
# socket/root-equivalent host access. That defeated the same
# least-privilege logic this project already applies elsewhere (the
# worker image deliberately has NO docker CLI at all, see
# worker/Dockerfile's own docstring, specifically so a worker-side
# capability can never become a coordinator-side one by accident).
# Splitting the file is the direct fix, not a workaround: each tool
# now enforces against its own list, in code (see bash_mcp_server.py's
# two separate FileAllowlist instances).
#
# One name per line; blank lines and '#' comments are ignored.
#
# This file lives under /app in the image (COPY'd, not bind-mounted).
# Changing it needs an image rebuild (make build/make start), not just
# an edit -- it's shared across every mounted named project, not tied
# to any one project's own directory.
#
# `docker` being allowlisted HERE already sets this container's
# privilege ceiling at "root-equivalent on the host" (the entire
# reason this container exists as a separate thing from every
# project's own service -- see Dockerfile and bash_mcp_server.py's
# docstring). Everything else below is narrower than that.
